동결 시점에 **무엇이 돌아가고 무엇을 남겼는지**를 적습니다. 남긴 것은 왜 지금이 아닌지까지

## 1. 종단 확인 — 일곱 명령 전부 통과

로컬(`localhost:8080`)과 dev(`api.dev.sbsh.cloud`)에서 각각 한 번씩 돌렸습니다.
실행기는 실제 배포 앱(`Slash.app`)을 썼고, dev 는 v0.5.7 로 페어링했습니다.

| 명령 | 작업 유형 | 실행 위치 | 로컬 | dev |
|---|---|---|---|---|
| `/요약` | `TEXT_SUMMARY` | `BACKEND` | 439ms | 통과 |
| `/날씨` | `WEATHER_LOOKUP` | `BACKEND` | 통과 | 통과 |
| `/상태` | `SYSTEM_STATUS` | `RUNNER` | 통과 | 통과 |
| `/파일` | `FILE_SEARCH` | `RUNNER` | 통과 | 통과 |
| `/열기` | `FILE_OPEN` | `RUNNER` | 통과 | 통과 |
| `/사용량` | `AI_AGENT_USAGE` | `RUNNER` | 통과 | 통과 |
| `/코드` | `CODE_ANALYSIS` | `RUNNER` | 30.4초 | 18.0초 |

`/코드` 를 뺀 나머지는 폴링 관측으로 1초 안에 끝났습니다. **폴링이 1초 간격이라 그보다
짧은 구간은 가르지 못합니다** — `439ms` 만 서버가 응답에 담아 준 실측값(`result.durationMs`)입니다.

**`/요약` 이 GPU 없이 도는 것을 확인한 것이 이번 확인의 목적이었습니다.**
`slash-infra#70` 으로 Ollama EC2 와 `slash-llm` 배포가 내려갔고 dev 의 `LLM_BASE_URL` 배선도
빠졌는데, `SUMMARY_ENGINE` 기본값이 `EXTRACTIVE` 라 그 값을 읽는 경로 자체가 없습니다.
결과에 `engine: EXTRACTIVE` · `algorithm: TFIDF_CENTROID` 가 담겨 오고, 7문장 원문이
3문장으로 나왔습니다.

`/사용량` 을 인자 없이 보내면 `NEEDS_CLARIFICATION` 으로 되묻습니다(정상 동작).

## 2. 동결 시점에 닫혀 있는 것

- **P0 는 전부 닫혔습니다.** 마지막이 승인 단계(`#60`, 8/21)였습니다
- **열린 PR 이 없습니다**
- **slash-docs#3 보안 검토의 동결 전 목록 중 slash-api 몫은 하나였고 `b42c2f6` 으로 끝났습니다** —
  `slash.text-summary.runner-enabled` 기본값 `false`. 꺼져 있어도 `TEXT_SUMMARY` 는 죽지 않고
  `resolveExecutionTarget` 이 `BACKEND` 로 보냅니다. 다시 열 때는 배포 없이 설정만 바꾸면 됩니다

## 3. 동결 후로 남긴 것

### `processing_route` 정리 (`#58`)

`execution_target` 을 들이면서 `processing_route` 를 남겨 두어 **두 열이 같은 것을 나눠
검증하고 있습니다.** 지금 지울 수 없는 이유는 이슈에 적어 두었고, 정리 조건 셋 중
**세 번째가 핵심**입니다 — 실행 위치 결정이 작업 유형 파생에서 벗어나야 합니다.
지금은 `resolveExecutionTarget()` 이 여전히 `processingRoute` 로 갈립니다.

### 계약 정의부터 필요한 것

slash-docs#3 의 감사 전송 경로·행동 단위 승인·레드팀 점검입니다. 마지막은 `TEXT_SUMMARY` 를
`RUNNER` 로 다시 여는 조건이기도 합니다. OS 수준 격리(네트워크 차단·파일시스템 샌드박스)가
생기기 전에는 그 경로를 열지 않기로 했습니다.

### 승인은 기반만 있고 쓰는 곳이 없습니다

`slash.approval.required-task-types` 가 비어 있는 것이 기본입니다. 지금 있는 작업은 모두
읽기 전용이거나 서버가 하는 일이라 물어볼 것이 없습니다. 승인이 필요한 작업이 생기면
**배포 없이 설정만으로** 켜집니다.

## 4. 운영할 때 걸리는 것 둘 (2026-08-26 실측)

### 실행기 v0.5.2 미만은 dev 에 아예 못 붙습니다

얼린 앱에 CA 인증서 번들이 빠져 있어 HTTPS·WSS 가 전부 `CERTIFICATE_VERIFY_FAILED` 로
죽습니다. slash-runner `#42` 로 8/21 에 고쳐졌고 **v0.5.2-pre 부터** 들어갔습니다.

**증상이 서버 쪽에서 보이지 않습니다** — 앱은 멀쩡히 떠 있고 TCP 연결을 하나도 맺지 않아,
페어링 요청이 서버에 도착하지 않고 `PENDING` 으로만 남습니다. localhost(HTTP)로는 잘 붙기
때문에 설정을 의심하게 됩니다. **시연·검증 전에 실행기 버전을 먼저 확인하는 편이 빠릅니다.**

### 그날 첫 명령이 `NLU_UNAVAILABLE` 로 실패할 수 있습니다

오늘 dev 에서 첫 `/파일` 이 이 코드로 실패했고, 곧바로 세 번 더 보내니 전부 통과했습니다
(0.1~1.1초). `slash.nlu.timeout` 이 2초라 콜드 스타트가 그 안에 못 들어온 것으로 보입니다.
인프라에 09~21시 가동 스케줄이 있어 **아침 첫 요청이 여기 걸립니다.** 과거 이력에도 같은
코드가 남아 있습니다.

재현되지 않아 원인을 확정하지 못했습니다. 시연 전에 아무 명령이나 한 번 보내
깨워 두는 것으로 피할 수 있습니다.
