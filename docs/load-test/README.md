# 부하 시험 — 어디가 먼저 막히는가

`2026-08-24` 측정. **목적은 "몇 RPS 가 나온다" 가 아니라 "무엇이 먼저 천장에 닿는가" 다.**
절대치는 측정 환경에 매이지만, 아래에서 찾은 **병목의 위치는 설정에서 오는 것이라 배포
환경에서도 같다.**

## 결론 먼저

| 경로 | 포화 처리량 | 그때 p95 | 먼저 막히는 것 |
|---|---|---|---|
| 이력 조회 `GET /api/v1/tasks` | **3,200 RPS** | 4ms (VU 10) | **Hikari 커넥션 10개** |
| 〃 (작업 결과가 19KB 일 때) | 375 → **2,344 RPS** | 15.0 → **2.8ms** | 쓰지도 않는 열을 읽고 있었다 — **이 PR 에서 고침** |
| 접수 `POST /api/v1/requests` (`/summary`) | **190 RPS** | 68ms (VU 10) | NLU CPU 요약 + 서버 쓰기 |
| (대조군) NLU 분석만 | 5,000 RPS | 3ms | — 관련 없음 |
| (대조군) NLU CPU 추출 요약만 | **405 RPS** | 28ms | **단일 워커 CPU** |

**병목이 하나가 아니라 둘이고, 서로 다른 곳에 있다.** 읽기는 커넥션 풀에서, 쓰기는
커넥션과 무관한 곳에서 막힌다.

## 측정 환경

절대치를 그대로 인용하면 안 되는 이유가 여기 있다 — **DB 가 같은 기계에 있어 네트워크
왕복이 없고**, 코어 수도 배포 노드와 다르다.

| | |
|---|---|
| 기계 | Apple M5 Pro · 15코어(성능 5 / 효율 10) · 24GB · macOS 26.6.2 |
| 런타임 | Java 21.0.10 · slash-api `dev`(`3d0eada`) jar |
| DB | PostgreSQL 16.14 (Docker, 같은 기계) |
| NLU | slash-nlu `dev` · uvicorn **워커 1개** (Dockerfile 기본값과 같음) |
| 도구 | k6 v2.1.0 |
| 자료 | 부하시험 사용자 20명 · 이력 10,000건 |

인증은 로컬 임시 인증(`Bearer <아무 문자열>`)이다. **실제 Cognito JWT 검증 비용은 이
측정에 들어 있지 않다.**

## 1. 이력 조회 — 커넥션 풀이 천장이다

| VUs | RPS | 실패 | avg | p95 | p99 | max | Hikari 활성/대기 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 5 | 2,230 | 0% | 2.2ms | 3ms | 4.1ms | 14.9ms | 5 / 0 |
| 10 | 3,191 | 0% | 3.1ms | 4ms | 4.7ms | 19.4ms | **10 / 0** |
| 20 | 3,183 | 0% | 6.2ms | 10.3ms | 13.4ms | 27.7ms | 10 / **10** |
| 40 | 3,190 | 0% | 12.5ms | 25.9ms | 37ms | 82.8ms | 10 / **30** |
| 80 | 3,200 | 0% | 24.9ms | 57.4ms | 82.9ms | 178.8ms | 10 / **71** |

**VU 10 에서 활성 커넥션이 상한(10)에 닿고, 그 뒤로는 처리량이 3,200 에서 멈춘 채
응답시간만 선형으로 늘어난다.** VU 를 8배(10→80) 올려도 RPS 는 그대로고 p95 만 14배가 된다.
대기 큐가 71까지 쌓인다.

**실패는 0% 다.** `connection-timeout: 3000` 안에는 결국 커넥션을 받기 때문에 터지지 않고
느려지기만 한다 — 장애로 드러나지 않아 더 늦게 발견될 종류다.

### 그리고 — 목록이 쓰지도 않는 열을 읽고 있었다 (고쳤다)

위 표는 결과가 작을 때다. **결과가 커지면 완전히 다른 그림이 된다.**

`findRecent` 가 `selectFrom(TASKS)` 로 **모든 열**을 읽고 있었다. 그런데 목록 응답
(`TaskSummaryResponse`)은 `parameters` 와 `result` 를 싣지 않는다 — 그 DTO 주석이 이유까지
정확히 적어 두었다.

> **`result` 와 `parameters` 는 싣지 않는다.** 결과는 한 건에 64KB 까지 허용되어 스무 줄이면
> 응답이 1MB 를 넘길 수 있는데, 목록 화면은 그 내용을 그리지 않는다.

**응답에서 뺄 이유는 알고 있었지만 쿼리는 그대로였다.** DB 에서 꺼내 앱까지 옮긴 뒤 버린다.

결과가 큰 이력 10,000건을 만들어 재봤다(VU 5). **결과의 압축률에 따라 값이 달라져 두 조건
모두 적는다.**

| 조건 | 수정 전 | 수정 후 | |
|---|---:|---:|---|
| 결과가 작을 때 | 2,350 RPS · p95 2.8ms | — | 기준 |
| 결과 20KB, **압축이 잘 되는** 내용(`repeat`) | 274 RPS · p95 23.3ms | 2,334 RPS · p95 2.9ms | 8.5배 |
| 결과 19KB, **압축이 안 되는** 내용(무작위) | **375 RPS · p95 15.0ms** | **2,344 RPS · p95 2.8ms** | **6.2배** |

**아래 줄이 실제에 가깝다.** 요약 결과는 반복 문자가 아니라 압축이 잘 듣지 않는다 — 위
조건은 19.3KB 가 0.4KB 로 저장되고, 아래는 19.3KB 가 19.4KB 그대로다. 압축된 쪽이 오히려
느린 것은 읽을 때 압축 해제 비용이 붙기 때문으로 보인다.

**아래 줄은 각 3회 측정했다** — 수정 전 369.1 / 375.7 / 381.2, 수정 후 2,366.9 / 2,297.9 /
2,366.3 RPS 로 편차가 3% 안이다.

고친 뒤에는 결과 크기가 조회 성능에 거의 영향을 주지 않는다 — 결과가 없을 때(2,350)와 같은
수준으로 돌아온다.

수정은 목록이 실제로 쓰는 열만 고르는 것이다(`TaskRepository.HISTORY_COLUMNS`).
응답 모양은 바뀌지 않아 계약 변경이 아니다.

```java
dsl.select(HISTORY_COLUMNS).from(TASKS)   // parameters · result 를 뺀다
```

**`input_text` 는 남겨 두었다.** `request_summary` 가 비어 있을 때 목록 문구를 그것으로 다시
만들기 때문이다(`RequestSummary`, 80자로 자름). 요약 원문이 8,000자까지 들어올 수 있어 이
열도 작지 않지만, SQL 에서 잘라 읽으면 자르는 규칙이 두 곳에 생긴다 — 남은 개선 여지다.

> **재현할 때 주의.** 이 절의 값은 이력 건수와 결과 크기에 크게 좌우된다. 시드 직후
> (사용자당 500건, 결과 작음)와 부하 시험을 한참 돌린 뒤(사용자당 1,600건)를 비교하면
> 같은 코드에서도 2,350 → 1,642 RPS 로 달라졌다. **비교하려면 `seed.sql` 로 초기화한 뒤
> 재는 것**이 맞다.

### 곁다리로 찾은 것 — 인증이 매 요청 DB 를 친다

`AuthenticatedUserService.current()` 가 요청마다 `userRepository.findByCognitoSub()` 를
부른다. 캐시가 없다. **이력 조회 한 번에 쿼리가 둘(사용자 + 목록)이고, 그만큼 커넥션을
두 배로 오래 잡는다.**

커넥션 수를 늘리지 않고 처리량을 올릴 수 있는 자리다. 다만 **정지 계정(`SUSPENDED`)
반영이 캐시 TTL 만큼 늦어지는 것**을 감수해야 하므로 그냥 넣을 것은 아니다.

## 3. 어디서 막히는지 가르기 (대조군)

접수 경로는 NLU 를 두 번 부른다 — 분석과 요약. 둘을 따로 쟀다.

**NLU 분석 (`/internal/v1/nlu/analyze`)**

| VUs | 5 | 10 | 20 | 40 |
|---|---:|---:|---:|---:|
| RPS | 4,734 | 4,926 | 5,036 | 5,240 |
| p95 | 1.6ms | 3ms | 5.5ms | 9.6ms |

**관련 없다.** 5,000 RPS 에서도 여유가 있다.

**CPU 추출 요약 (`/internal/v1/nlu/summaries/extractive`)**

| VUs | 5 | 10 | 20 | 40 |
|---|---:|---:|---:|---:|
| RPS | 412 | 416 | 405 | 394 |
| p95 | 14.5ms | 28.2ms | 58.8ms | 120.1ms |

**405 RPS 에서 평평해지고 응답시간이 동시성에 정비례한다.** 전형적인 단일 프로세스
CPU 바운드 형태다.

`slash-nlu/Dockerfile` 의 마지막 줄이 근거다.

```dockerfile
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

**`--workers` 가 없다.** 로컬에서만 그런 것이 아니라 배포도 워커 하나로 돈다. 위 측정이
곧 배포 특성이다.

### 남은 절반은 서버 몫이다

요약 단독이 405 RPS 인데 접수는 190 RPS 다. VU 40 기준으로 접수 209ms 중 요약이 101ms 이니
**나머지 108ms 는 서버에서 쓴다.**

접수 한 건은 `CREATED → ANALYZING → QUEUED → RUNNING → SUCCEEDED` 로 **네 번 전이하고**
그때마다 이벤트를 적고 WSS 로 알린다(실측으로 확인한 전이다).

**`2026-08-25` 에 갈라 봤다. 이벤트 기록이다.** 후보를 하나씩 없앤 판을 만들어 재는 방식으로
셋을 확인했다.

| 후보 | 결과 |
|---|---|
| DB 커밋 횟수 | **아니다** — 셋을 하나로 묶어도 안 변한다 |
| WSS 발행 | **아니다** — 통째로 없애도 안 변한다 |
| **이벤트 기록** | **이것이다** — 없애면 **+13%**, p95 도 유일하게 좋아진다 |

#### 하나 — DB 커밋 횟수는 아니다

`2026-08-25` 측정. `#70` 을 고치면서 **접수 한 건의 커밋이 셋에서 하나로 줄었다.**

    전:  taskRepository.create + recordCreated(@Transactional) + tryInsert(auto-commit)
    후:  stateWriter.create 한 트랜잭션 안에서 셋

108ms 의 일부가 여기라면 처리량이 올랐어야 한다. 고치기 전(`b42c2f6`)과 후(`0181631`)를
같은 기계·같은 시드로 각 **3회씩** 쟀다.

| | 회차별 RPS | 평균 | 범위폭 |
|---|---|---:|---:|
| VU 10 · 고치기 전 | 217.7 / 216.2 / 216.4 | 216.8 | 0.7% |
| VU 10 · 고친 뒤 | 212.3 / 224.6 / 216.4 | 217.8 | 5.6% |
| VU 40 · 고치기 전 | 227.7 / 209.4 / 224.3 | 220.5 | 8.3% |
| VU 40 · 고친 뒤 | 226.9 / 219.8 / 236.3 | 227.7 | 7.2% |

**차이는 +0.5% 와 +3.3% 로 둘 다 측정 편차보다 작다.** 커밋 횟수는 이 경로의 지배적
요인이 아니다. 남은 후보는 위에 적은 **네 번의 전이와 그때마다의 이벤트 기록·WSS 발행**이다.

절대치가 위 표(190 RPS)보다 높은 것은 **측정 조건이 달라서다** — 그날은 없던 로컬
Kubernetes 파드가 함께 돌고 있었고 slash-nlu 도 `09e7df0` 로 올라가 있었다. 그래서 이
절은 8/24 값과 견주지 않고 **같은 자리에서 잰 두 판만** 비교한다.

> **한 번만 재면 반대 결론이 나온다.** 처음에 각 1회씩 쟀을 때는 VU 10 에서 +8.1%,
> VU 40 에서 +8.2% 가 나왔다. 그런데 고치기 전 첫 측정이 205.4 였다가 반복하면 216~218 로
> 올라간다 — **JIT 워밍업 차이였다.** 접수 경로를 비교할 때는 한 회차를 버리고 3회 이상
> 재야 한다.

#### 나머지 둘 — WSS 발행도 아니다. 이벤트 기록이다

후보를 하나씩 지운 판을 만들어(`WsMessagePublisher.publish` · `TaskEventRepository.append` 를
각각 즉시 반환하게 고쳐 빌드) 잰다. **기준을 사이사이에 끼워 세 번 잰 것이 핵심이다** —
아래 표를 보면 기준 자체가 240 → 228 → 219 로 계속 내려간다. 기준을 한 번만 잡았으면
그 하락을 개선이나 퇴보로 잘못 읽는다.

| 잰 순서 (VU 10, 각 3회) | 회차별 RPS | 평균 | p95 |
|---|---|---:|---:|
| 기준 (1차) | 238.1 / 240.6 / 241.8 | 240.2 | 51.6 |
| **WSS 발행 no-op** | 203.5 / 237.7 / 236.2 | 225.8 | 54.8 |
| 기준 (2차) | 227.9 / 231.7 / 226.0 | 228.5 | 53.0 |
| **이벤트 기록 no-op** | 257.8 / 258.1 / 261.0 | **259.0** | **46.6** |
| 기준 (3차) | 197.4 / 226.1 / 233.6 | 219.0 | 57.3 |

드리프트가 있으므로 평균이 아니라 **범위가 겹치는지**로 읽는다.

- **WSS 발행 no-op** — `203.5 ~ 237.7`. 기준 범위(`197.4 ~ 241.8`) 안에 그대로 들어간다.
  발행을 통째로 없애도 달라지지 않는다. Valkey 가 같은 기계이고 직렬화 대상도 작은 객체라
  다섯 번을 해도 ms 단위다
- **이벤트 기록 no-op** — `257.8 ~ 261.0`. **기준의 가장 좋은 값(241.8)보다 최저값이 높아
  겹치지 않는다.** 회차 편차도 1.2% 로 가장 작고, p95 가 50 아래로 내려간 유일한 판이다

**왜 큰지는 코드가 설명한다.** `TaskEventRepository.append` 는 단순 INSERT 가 아니다.

```sql
SELECT id FROM tasks WHERE id = ? FOR UPDATE           -- 같은 행을 잠근다
SELECT coalesce(max(sequence), 0) + 1 FROM task_events -- 채번
INSERT INTO task_events ...
```

**쿼리 세 번에 행 잠금 하나**이고, 접수 한 건이 다섯 번 부른다(최초 기록 + 전이 넷). 즉
**쿼리 15회와 같은 `tasks` 행 잠금 5회**다. 동시성이 올라가면 그 잠금이 서로를 기다린다 —
이 판만 p95 가 함께 좋아지는 것이 그 신호다.

커밋을 셋에서 하나로 묶어도 안 변한 이유가 여기 있다. **값을 쓰는 것은 커밋 횟수가 아니라
쿼리 횟수와 행 잠금이다.**

> **지워도 된다는 뜻이 아니다.** 타임라인은 화면의 진행 표시라 없앨 수 없다(`TaskStateWriter`
> 클래스 주석). 손댄다면 `sequence` 채번에서 행 잠금을 걷어내거나 전이 횟수를 줄이는 쪽인데,
> 둘 다 설계 결정이라 여기서 정할 것이 아니다.

## 재현 방법

```bash
# 1. DB·NLU 를 띄운다
docker compose up -d
(cd ~/slash-nlu && .venv/bin/python -m uvicorn main:app --host 127.0.0.1 --port 8001)

# 2. 시드
docker exec -i slash-postgres psql -U slash -d slash < docs/load-test/seed.sql

# 3. slash-api 는 jar 로 띄운다 — bootRun 은 .env 의 COGNITO_ISSUER_URI 를 읽어
#    실제 Cognito 모드로 넘어가면서 임시 인증이 꺼진다.
#    Hikari 를 관측하려면 metrics 노출을 켠다(운영 기본값은 health,info 뿐이다).
./gradlew bootJar
env -u COGNITO_ISSUER_URI \
  MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,info,metrics \
  java -jar build/libs/slash-api-0.0.1-SNAPSHOT.jar

# 4. 측정 — 동시성을 계단으로 올린다
docs/load-test/run.sh read  5 10 20 40 80
docs/load-test/run.sh write 5 10 20 40
```

`run.sh` 는 각 단계마다 k6 를 돌리면서 Hikari 활성·대기를 0.5초 간격으로 함께 찍는다.
결과는 `res-<시나리오>-<VUs>.json` 과 `hikari-<시나리오>-<VUs>.txt` 로 남는다.

`metrics` 엔드포인트는 인증이 필요하다 — `PUBLIC_PATHS` 의 actuator 경로는 `health`·`info` 뿐이다.
`run.sh` 가 `Bearer loadops` 를 쓴다.

## 고친 것이 응답을 바꾸지 않았는지

성능만 보고 넘기지 않으려고, **수정 전(`dev` `3d0eada`)과 수정 후의 응답을 실제로 받아
비교했다.** 모든 필드가 채워진 작업 26건(성공·실패 섞고, `request_summary` 가 빈 행도 하나)을
만들어 두고

- 목록 첫 쪽 (`limit=20`)
- 커서로 받은 다음 쪽
- 상태로 좁힌 조회 (`status=FAILED`)

셋을 받아 `meta`(매번 달라지는 `requestId`·`serverTime`)만 빼고 견주었다. **336줄이 완전히
같다.** `request_summary` 가 빈 행이 `input_text` 로 대체되는 경로도 그대로다.

## 동시성 정합성 — 빠른가 말고 틀리지 않는가

처리량과 별개로 **동시에 들어올 때 결과가 어긋나지 않는지**를 봤다. 20건을 동시에 쏘는 방식이다.

| 무엇 | 결과 | |
|---|---|---|
| 같은 `Idempotency-Key` 로 접수 | 응답 1종류 · `tasks` 1건 · 이력 1줄 | ✅ `#70` 으로 고침 |
| 같은 키로 브라우저 요약 결과 제출 | 응답 1종류 · `tasks` 1건 · 이력 1줄 | ✅ `#70` 으로 고침 |
| 같은 PC 로 서로 다른 요청 | `QUEUED` 1 + `DEVICE_BUSY` 19 · 전달 1건 | ✅ |

**앞의 둘은 처음 재면서 발견해 고친 것이다.** 그때는 **멱등이 응답에서만 지켜지고 저장에서는
아니었다** — `accept()` 가 작업을 먼저 만든 뒤 키를 선점해서, 경쟁에 진 요청이 만들어 둔
작업 19건이 사용자 이력 화면에 `CREATED` 로 그대로 남았다. 브라우저 요약 결과 제출(`#65`)도
같은 경로를 쓰므로 같이 새고 있었다.

**작업 생성·최초 기록·키 선점을 한 트랜잭션으로 묶어 고쳤다**(`TaskStateWriter.create`).
선점하지 못하면 그 트랜잭션을 통째로 되돌리므로, 진 요청의 작업은 지워지는 것이 아니라
애초에 만들어지지 않는다. 위 표의 값은 고친 뒤 같은 절차로 다시 잰 것이다.

기기 경쟁은 `uk_dispatch_active_device` 와 `dispatchOrRelease` 가 설계대로 동작한다.

> **기기 경쟁은 Agent 없이 재현되지 않는다.** WSS 연결이 없으면 하트비트 스윕이 기기를
> `OFFLINE` 으로 내려 전부 `WAITING_FOR_DEVICE` 가 된다. `SLASH_SCHEDULING_ENABLED=false`
> 로 스윕을 끄고 기기를 `READY` 로 되돌린 뒤에야 경쟁이 드러난다.

## 아직 재지 않은 것

- **WSS 동시 접속** — 기기 수가 늘 때 `WsSessionRegistry`·Valkey Pub/Sub 이 어떻게 되는지
- **실제 Cognito JWT 검증 비용** — 로컬 임시 인증에는 없다
- ~~**접수 경로의 서버 몫 108ms 의 내역**~~ — **갈랐다. 이벤트 기록이다**(위 참고).
  커밋 횟수도 WSS 발행도 아니었다
- **dev 에서의 재측정** — 절대치는 이 기계의 것이다
