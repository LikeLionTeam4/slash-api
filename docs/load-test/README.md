# 부하 시험 — 어디가 먼저 막히는가

`2026-08-24` 측정. **목적은 "몇 RPS 가 나온다" 가 아니라 "무엇이 먼저 천장에 닿는가" 다.**
절대치는 측정 환경에 매이지만, 아래에서 찾은 **병목의 위치는 설정에서 오는 것이라 배포
환경에서도 같다.**

## 결론 먼저

| 경로 | 포화 처리량 | 그때 p95 | 먼저 막히는 것 |
|---|---|---|---|
| 이력 조회 `GET /api/v1/tasks` | **3,200 RPS** | 4ms (VU 10) | **Hikari 커넥션 10개** |
| 〃 (작업 결과가 20KB 일 때) | 274 → **2,334 RPS** | 23.3 → **2.9ms** | 쓰지도 않는 열을 읽고 있었다 — **이 PR 에서 고침** |
| 접수 `POST /api/v1/requests` (`/summary`) | **190 RPS** | 68ms (VU 10) | NLU CPU 요약 + 서버 쓰기 |
| (대조군) NLU 분석만 | 5,000 RPS | 3ms | — 관련 없음 |
| (대조군) NLU CPU 추출 요약만 | **405 RPS** | 28ms | **단일 워커 CPU** |

**병목이 하나가 아니라 둘이고, 서로 다른 곳에 있다.** 읽기는 커넥션 풀에서, 쓰기는
커넥션과 무관한 곳에서 막힌다.

## 측정 환경

절대치를 그대로 인용하면 안 되는 이유가 여기 있다 — **DB 가 같은 기계에 있어 네트워크
왕복이 없고**, 코어 수도 배포 노드와 다르다.

| | |
|---|---|
| 기계 | Apple M5 Pro · 15코어(성능 5 / 효율 10) · 24GB · macOS 26.6.2 |
| 런타임 | Java 21.0.10 · slash-api `dev`(`3d0eada`) jar |
| DB | PostgreSQL 16.14 (Docker, 같은 기계) |
| NLU | slash-nlu `dev` · uvicorn **워커 1개** (Dockerfile 기본값과 같음) |
| 도구 | k6 v2.1.0 |
| 자료 | 부하시험 사용자 20명 · 이력 10,000건 |

인증은 로컬 임시 인증(`Bearer <아무 문자열>`)이다. **실제 Cognito JWT 검증 비용은 이
측정에 들어 있지 않다.**

## 1. 이력 조회 — 커넥션 풀이 천장이다

| VUs | RPS | 실패 | avg | p95 | p99 | max | Hikari 활성/대기 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 5 | 2,230 | 0% | 2.2ms | 3ms | 4.1ms | 14.9ms | 5 / 0 |
| 10 | 3,191 | 0% | 3.1ms | 4ms | 4.7ms | 19.4ms | **10 / 0** |
| 20 | 3,183 | 0% | 6.2ms | 10.3ms | 13.4ms | 27.7ms | 10 / **10** |
| 40 | 3,190 | 0% | 12.5ms | 25.9ms | 37ms | 82.8ms | 10 / **30** |
| 80 | 3,200 | 0% | 24.9ms | 57.4ms | 82.9ms | 178.8ms | 10 / **71** |

**VU 10 에서 활성 커넥션이 상한(10)에 닿고, 그 뒤로는 처리량이 3,200 에서 멈춘 채
응답시간만 선형으로 늘어난다.** VU 를 8배(10→80) 올려도 RPS 는 그대로고 p95 만 14배가 된다.
대기 큐가 71까지 쌓인다.

**실패는 0% 다.** `connection-timeout: 3000` 안에는 결국 커넥션을 받기 때문에 터지지 않고
느려지기만 한다 — 장애로 드러나지 않아 더 늦게 발견될 종류다.

### 그리고 — 목록이 쓰지도 않는 열을 읽고 있었다 (고쳤다)

위 표는 결과가 작을 때다. **결과가 커지면 완전히 다른 그림이 된다.**

`findRecent` 가 `selectFrom(TASKS)` 로 **모든 열**을 읽고 있었다. 그런데 목록 응답
(`TaskSummaryResponse`)은 `parameters` 와 `result` 를 싣지 않는다 — 그 DTO 주석이 이유까지
정확히 적어 두었다.

> **`result` 와 `parameters` 는 싣지 않는다.** 결과는 한 건에 64KB 까지 허용되어 스무 줄이면
> 응답이 1MB 를 넘길 수 있는데, 목록 화면은 그 내용을 그리지 않는다.

**응답에서 뺄 이유는 알고 있었지만 쿼리는 그대로였다.** DB 에서 꺼내 앱까지 옮긴 뒤 버린다.

결과가 20KB 인 이력 10,000건을 만들어 재봤다(VU 5 기준).

| | RPS | p95 |
|---|---:|---:|
| 결과가 작을 때 | 2,350 | 2.8ms |
| **결과 20KB · 수정 전** | **274** | **23.3ms** |
| **결과 20KB · 수정 후** | **2,334** | **2.9ms** |

**8.5배다.** 고친 뒤에는 결과 크기가 조회 성능에 거의 영향을 주지 않는다 — 결과가 없을 때
(2,350)와 같은 수준으로 돌아온다.

수정은 목록이 실제로 쓰는 열만 고르는 것이다(`TaskRepository.HISTORY_COLUMNS`).
응답 모양은 바뀌지 않아 계약 변경이 아니다.

```java
dsl.select(HISTORY_COLUMNS).from(TASKS)   // parameters · result 를 뺀다
```

**`input_text` 는 남겨 두었다.** `request_summary` 가 비어 있을 때 목록 문구를 그것으로 다시
만들기 때문이다(`RequestSummary`, 80자로 자름). 요약 원문이 8,000자까지 들어올 수 있어 이
열도 작지 않지만, SQL 에서 잘라 읽으면 자르는 규칙이 두 곳에 생긴다 — 남은 개선 여지다.

> **재현할 때 주의.** 이 절의 값은 이력 건수와 결과 크기에 크게 좌우된다. 시드 직후
> (사용자당 500건, 결과 작음)와 부하 시험을 한참 돌린 뒤(사용자당 1,600건)를 비교하면
> 같은 코드에서도 2,350 → 1,642 RPS 로 달라졌다. **비교하려면 `seed.sql` 로 초기화한 뒤
> 재는 것**이 맞다.

### 곁다리로 찾은 것 — 인증이 매 요청 DB 를 친다

`AuthenticatedUserService.current()` 가 요청마다 `userRepository.findByCognitoSub()` 를
부른다. 캐시가 없다. **이력 조회 한 번에 쿼리가 둘(사용자 + 목록)이고, 그만큼 커넥션을
두 배로 오래 잡는다.**

커넥션 수를 늘리지 않고 처리량을 올릴 수 있는 자리다. 다만 **정지 계정(`SUSPENDED`)
반영이 캐시 TTL 만큼 늦어지는 것**을 감수해야 하므로 그냥 넣을 것은 아니다.

## 2. 접수 — 커넥션은 놀고 있다

| VUs | RPS | 실패 | avg | p95 | p99 | max | Hikari 활성/대기 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 5 | 178 | 0% | 28.1ms | 33.7ms | 37.1ms | 594.4ms | 5 / 0 |
| 10 | 189 | 0% | 52.7ms | 67.9ms | 84.3ms | 196.7ms | 6 / 0 |
| 20 | 199 | 0% | 100.5ms | 124.7ms | 161.6ms | 228.3ms | 10 / 10 |
| 40 | 191 | 0% | 209.4ms | 279.9ms | 341ms | 438.5ms | **8 / 0** |

**VU 40 에서도 활성 8, 대기 0 이다.** 읽기와 달리 커넥션 풀이 병목이 아니다. 190~200 RPS
에서 포화하고 응답시간이 동시성에 정비례한다.

## 3. 어디서 막히는지 가르기 (대조군)

접수 경로는 NLU 를 두 번 부른다 — 분석과 요약. 둘을 따로 쟀다.

**NLU 분석 (`/internal/v1/nlu/analyze`)**

| VUs | 5 | 10 | 20 | 40 |
|---|---:|---:|---:|---:|
| RPS | 4,734 | 4,926 | 5,036 | 5,240 |
| p95 | 1.6ms | 3ms | 5.5ms | 9.6ms |

**관련 없다.** 5,000 RPS 에서도 여유가 있다.

**CPU 추출 요약 (`/internal/v1/nlu/summaries/extractive`)**

| VUs | 5 | 10 | 20 | 40 |
|---|---:|---:|---:|---:|
| RPS | 412 | 416 | 405 | 394 |
| p95 | 14.5ms | 28.2ms | 58.8ms | 120.1ms |

**405 RPS 에서 평평해지고 응답시간이 동시성에 정비례한다.** 전형적인 단일 프로세스
CPU 바운드 형태다.

`slash-nlu/Dockerfile` 의 마지막 줄이 근거다.

```dockerfile
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

**`--workers` 가 없다.** 로컬에서만 그런 것이 아니라 배포도 워커 하나로 돈다. 위 측정이
곧 배포 특성이다.

### 남은 절반은 서버 몫이다

요약 단독이 405 RPS 인데 접수는 190 RPS 다. VU 40 기준으로 접수 209ms 중 요약이 101ms 이니
**나머지 108ms 는 서버에서 쓴다.**

접수 한 건은 `CREATED → ANALYZING → QUEUED → RUNNING → SUCCEEDED` 로 **네 번 전이하고**
그때마다 이벤트를 적고 WSS 로 알린다(실측으로 확인한 전이다). 유력한 후보지만 **아직 갈라 보지 않았다** — 무엇이
지배적인지 확인하기 전에는 추측이다.

## 재현 방법

```bash
# 1. DB·NLU 를 띄운다
docker compose up -d
(cd ~/slash-nlu && .venv/bin/python -m uvicorn main:app --host 127.0.0.1 --port 8001)

# 2. 시드
docker exec -i slash-postgres psql -U slash -d slash < docs/load-test/seed.sql

# 3. slash-api 는 jar 로 띄운다 — bootRun 은 .env 의 COGNITO_ISSUER_URI 를 읽어
#    실제 Cognito 모드로 넘어가면서 임시 인증이 꺼진다.
#    Hikari 를 관측하려면 metrics 노출을 켠다(운영 기본값은 health,info 뿐이다).
./gradlew bootJar
env -u COGNITO_ISSUER_URI \
  MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,info,metrics \
  java -jar build/libs/slash-api-0.0.1-SNAPSHOT.jar

# 4. 측정 — 동시성을 계단으로 올린다
docs/load-test/run.sh read  5 10 20 40 80
docs/load-test/run.sh write 5 10 20 40
```

`run.sh` 는 각 단계마다 k6 를 돌리면서 Hikari 활성·대기를 0.5초 간격으로 함께 찍는다.
결과는 `res-<시나리오>-<VUs>.json` 과 `hikari-<시나리오>-<VUs>.txt` 로 남는다.

`metrics` 엔드포인트는 인증이 필요하다 — `PUBLIC_PATHS` 의 actuator 경로는 `health`·`info` 뿐이다.
`run.sh` 가 `Bearer loadops` 를 쓴다.

## 아직 재지 않은 것

- **WSS 동시 접속** — 기기 수가 늘 때 `WsSessionRegistry`·Valkey Pub/Sub 이 어떻게 되는지
- **기기당 동시 1건 경쟁** (`uk_dispatch_active_device`) — 같은 기기로 동시에 들어올 때
- **멱등키 경쟁** — 같은 `Idempotency-Key` 동시 요청
- **실제 Cognito JWT 검증 비용** — 로컬 임시 인증에는 없다
- **접수 경로의 서버 몫 108ms 의 내역**

## 다음

우리 규모에서 3,200 RPS · 190 RPS 는 부족하지 않다. **이 문서의 값은 "고쳐야 할 장애" 가
아니라 "한계가 어디이고 왜 거기인지" 의 기록이다.** 손댄다면 순서는 이렇다.

| 후보 | 무엇 | 어디 몫 |
|---|---|---|
| 사용자 조회 캐시 | 읽기 요청당 쿼리 2→1. 커넥션을 안 늘리고 처리량을 올린다 | slash-api |
| 목록에서 `input_text` 도 빼기 | 요약 원문이 8,000자까지 들어온다. 자르는 규칙이 두 곳에 생기는 것을 감수할지 판단이 먼저다 | slash-api |
| NLU 워커 수 | `Dockerfile` `CMD` 에 `--workers`. 쓰기 병목의 절반 | slash-nlu |
| 접수 경로 서버 비용 | 먼저 무엇이 108ms 를 쓰는지 갈라야 한다 | slash-api |
| Hikari 풀 크기 | 가장 빠르지만, 설정 주석이 RDS `max_connections` 를 근거로 든다 — 사양 확인이 먼저다 | slash-api · infra |
